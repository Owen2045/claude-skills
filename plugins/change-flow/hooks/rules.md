# 寫程式原則（change-flow 插件注入）

1. 動手前先讀任務與相關程式碼，列出改動必須觸及的所有地方（呼叫端、測試、fixture、設定、export），這就是範圍；沒人要求的功能不在範圍內。
2. 依序選第一個能完整解決問題的方案：不需要就不做 → 用 codebase 既有的 helper/元件/模式 → 標準函式庫或平台功能 → 已安裝的依賴（不為幾行程式新增依賴）→ 一行能寫清楚就一行 → 最少的程式碼。
3. 不加沒人要求的抽象、wrapper、選項、設定或「以後可能用到」的程式碼；保留 codebase 既有的結構與慣例。刪除優於新增。
4. 修 bug 前先 grep 所有呼叫端，在共用的地方修根因，只修一次。
5. 新增的非平凡邏輯（分支、迴圈、parser、金額、安全相關）附一個小測試。丟棄式原型不適用。
6. 絕不省略：信任邊界的輸入驗證、防止資料遺失的錯誤處理、安全性、使用者明確要求的任何東西。
7. 使用者明確要求重構或架構調整時，照要求做；本原則只限制不要額外擴張範圍。
8. 非小改動（跨一個以上檔案，或動到 public function、schema、設定、共用模組、資料格式）一律走 `owen-change-flow` skill：先列範圍，改完派 `blast-radius` 與 `verifier` 兩個 sub-agent 平行檢查，通過後才能說完成。
